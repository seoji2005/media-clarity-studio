### M-01 잔여 실패 시나리오와 최소 수정

- ADR-0011을 기준으로 모듈을 만들면 `translate`가 다시 빠집니다.
- `ARCHITECTURE.md`의 §3.4 참조를 따라가면 정의가 없어 두 축 계약 위치를 찾지 못합니다.
- §8 scorecard를 그대로 구현하면 target 축이 사람용 리포트에서 누락되거나 축 없는 지표로 보일 수 있습니다.
- U-22를 DECISIONS 정의만 보고 처리하면 번역 어댑터·공급자 결정의 추적 ID가 사라집니다.

**최소 안전 수정:** ADR-0011을 11개 모듈로 맞추고 `translate`를 추가합니다. §3의 두 `§3.4` 참조를 실제 §3.0.1로 고칩니다. EVALS §8 scorecard에 source/target 축 칸 또는 분리 표를 넣되 구체 번역 지표는 정하지 않습니다. DECISIONS의 U-22 정의를 다른 문서와 같은 범위로 맞춥니다.

**수정 후 확인:** 위 네 잔여 위치만 새 고정 HEAD에서 대조하고, 모델·공급자·목표 언어·목표 수치가 여전히 미결정인지 확인합니다.

### 3.2 `STATUS.md`의 `f001ace…` “새 HEAD” — **잔여 M-02 결함**

`STATUS.md` 머리말과 §4 TASK-012 행은 `f001acecc1e20f88b4625428e6ac136208d4c718`을 **“새 HEAD”**라고 부릅니다. 주변 표가 이 SHA를 “M-01·M-02 실질 수정 커밋”으로도 설명하고, PR #5 본문 §7이 후속 `e0d99cf…`는 상태 표시만 바꿨다고 밝히므로 **수정 내용의 출처**가 `f001ace…`라는 뜻은 이해할 수 있습니다.

그러나 `STATUS.md`는 현재 상태의 권위 문서이고, “새 HEAD에서 제한 재검토”는 검토 대상을 지정하는 표현입니다. GitHub의 실제 대상 브랜치 HEAD와 이번 고정 대상은 `e0d99cf8e69e33eb271702a6c0ff3d403891a18a`입니다. 따라서 이 문구를 “실질 수정 커밋”으로만 읽어야 한다는 숨은 전제가 필요하며, 새 세션이 `f001ace…`를 고정 대상 HEAD로 잡는 재현 가능한 오도가 남습니다.

**판정:** 자동 실패가 아니라 문맥을 대조한 결과, 실질 수정 커밋 표기 의도는 인정하지만 현재 HEAD라는 사실 표기는 틀리므로 **M-02 부분 해소**입니다.

**최소 안전 수정:** `f001ace…`를 “실질 수정 커밋”으로 명시하고 “현재/새 HEAD”는 `e0d99cf…`로 기록합니다. 또는 검토 대상 SHA를 PR #5의 실제 HEAD로만 표현합니다.

**수정 후 확인:** STATUS 머리말·§2.3 TASK-012 상태·§4 현재 진행 중의 검토 대상 SHA가 GitHub HEAD와 일치하고, 그래프·제안 상태·역사 판정 분리는 그대로인지 확인합니다.

### 3.3 `DECISIONS.md`의 코드 구현 노드 누락 — **잔여 M-02 결함**

`PLAN.md` §3-1d, `STATUS.md` §4, `TASK-012.md` §6은 모두 “코드 구현 — TASK-006까지 완료 후” 행을 둡니다. `DECISIONS.md` §4.1.3의 같은 그래프 표는 TASK-006에서 끝나므로, 요청된 여섯 번째 노드가 네 문서에서 동일하게 도출되지 않습니다. 상위 계획과 충돌하는 조기 구현 허용 문구는 없지만, “네 곳에 같은 그래프”라는 주장과 실제 구조는 다릅니다.

**최소 안전 수정:** `DECISIONS.md` §4.1.3 표에 “코드 구현 — TASK-006까지 완료 후” 행을 추가합니다. 제안 상태나 U-31 범위는 바꾸지 않습니다.

**수정 후 확인:** 네 문서의 표가 여섯 노드를 모두 같은 선행으로 표현하는지 확인합니다.

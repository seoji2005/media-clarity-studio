# DECISIONS.md — 결정 기록

무엇이 정해졌고, 무엇이 제안일 뿐이며, 무엇이 아직 모르는 것인가.

마지막 갱신: 2026-08-09 (Phase 0)

---

## 상태 표기

| 라벨 | 의미 | 바꾸려면 |
|---|---|---|
| **승인됨 (Accepted)** | 확정. 이 위에 다른 것을 쌓아도 됨 | 사람 제품 오너 승인 + PR |
| **제안됨 (Proposed)** | 합리적 제안이나 아직 검증·합의 전. 반박 가능 | 리뷰에서 반대 근거 제시 |
| **미해결 (Unresolved)** | 답을 모름. **추측으로 채우지 않음** | 사실 확인 또는 측정 필요 |
| **보류됨 (Deferred)** | 지금 결정하면 손해. 의도적으로 미룸 | 지정된 단계 도달 시 재검토 |

**중요:** 문서에서 어떤 항목의 상태가 불명확하면 **미해결로 간주**합니다.
"아마 이럴 것이다"를 승인된 것처럼 다루지 않습니다.

## 1. 승인됨 (Accepted)

이 결정들은 [`../AGENTS.md`](../AGENTS.md)와 [`../PLAN.md`](../PLAN.md)에 이미 반영되어 있습니다.

---

### ADR-0001 — Phase 0에서는 코드를 쓰지 않는다 (문서 우선)

**맥락:** 요구사항이 불확실하고, 서로 대화를 볼 수 없는 여러 에이전트가 병렬 작업해야 함.
**결정:** Phase 0의 산출물은 문서뿐. 기능 코드·의존성·모델·CI·비밀정보를 추가하지 않는다.
**근거:** 공유 전제 없이 시작한 코드는 나중에 전부 버려야 함. 문서는 코드보다 고치기 싸다.
**결과:** 착수가 느려 보이지만, 두 에이전트가 같은 계약 위에서 병렬 작업할 수 있게 된다.
**되돌리기:** Phase 1 진입 시 자연스럽게 해제.

---

### ADR-0002 — "복원"이 아니라 "재구성/추정"으로 기술한다

**맥락:** mosaic·blur는 정보를 실제로 삭제한다. 원본은 알 수 없다.
**결정:** 모든 영상 개선 결과를 재구성(reconstruction) 또는 추정(estimation)으로 기술한다.
"원본 복원", "원본과 동일" 류의 표현을 코드·UI·문서·커밋 어디에도 쓰지 않는다.
**근거:** 사실이 아니다. 학술적으로는 허위 주장이고, 상업적으로는 소비자 기만이 된다.
**결과:** UI와 리포트가 항상 불확실성을 표시한다. `is_estimate`는 상수 true (ADR-0016).
**되돌리기:** 없음. 이 결정은 되돌리지 않는다.

---

### ADR-0003 — Local-first를 기본값으로 한다

**결정:** 네트워크 없이 동작하는 것이 기본. 클라우드 전송은 사용자가 켜는 선택 기능.
**근거:** 사용자 미디어는 민감할 수 있다. 크리에이터는 소재 유출을 우려한다.
로컬 전용으로도 제품이 완결되어야 클라우드가 선택지가 된다.
**결과:** `export` 모듈이 선택적 주변부가 된다 (Phase 4). 처리 성능은 사용자 PC에 달린다.

---

### ADR-0004 — 자막을 먼저, 영상 재구성을 그 다음에 한다

**결정:** Phase 1 = 자막 + 평가, Phase 2 = 영상 재구성.
**근거:** 자막은 정량 평가가 가능하고, 영상 재구성은 주관성이 크다.
측정 가능한 쪽을 먼저 세워야 판단 기준이 생긴다. 과제 채점 대상도 자막이 중심이다.
**결과:** 영상 재구성이 늦어진다. 기한이 촉박하면 Phase 2를 포기할 수 있다 (U-11 확인 필요).

---

### ADR-0005 — 합성 열화 기반으로 평가한다

**맥락:** 채점 원본이 비공개라 실제 정답과 비교할 수 없다.
**결정:** 정답을 아는 깨끗한 데이터에 우리가 열화를 가해 평가 세트를 만든다.
**근거:** 유일하게 신뢰 가능한 측정 신호. 대안이 없다.
**결과:** 분포 불일치 위험을 영구적으로 안고 간다 ([`EVALS.md`](EVALS.md) §9).
이 위험은 제거 불가이며 완화만 가능하다.

---

### ADR-0006 — 에이전트는 브랜치와 PR로만 협업한다

**결정:** TASK당 구현 소유자 1명, 리뷰어는 다른 에이전트. `main` 직접 수정 금지.
인계는 저장소 파일과 PR 설명으로만.
**근거:** Claude와 Codex는 서로의 대화를 볼 수 없다. 저장소가 유일한 공유 매체다.
**결과:** 문서화 부담이 늘지만, 세션이 끊겨도 작업이 이어진다.

---

### ADR-0007 — 사람이 읽는 설명은 한국어, 식별자는 영어

**결정:** 산문은 한국어. 파일명·명령어·코드 식별자·정착된 기술 용어는 영어 유지.
**근거:** 제품 오너가 한국어 화자이며 개발 경험이 많지 않다. 이해가 정확성보다 먼저다.
동시에 식별자를 번역하면 검색·도구 연동·재현성이 깨진다.

---

### ADR-0008 — `AGENTS.md`가 규칙의 단일 출처다

**결정:** 규칙 충돌 시 `AGENTS.md`가 이긴다. `CLAUDE.md`는 규칙을 복제하지 않고 참조만 한다.
**근거:** 규칙이 여러 곳에 복제되면 갈라지고, 에이전트마다 다른 규칙을 따르게 된다.

---

### ADR-0009 — `main`을 직접 수정하거나 병합하지 않는다

**결정:** 에이전트는 항상 리뷰 가능한 PR을 남긴다. 병합은 사람이 결정한다.
**근거:** 제품 오너가 모든 변경을 볼 수 있어야 한다. 되돌릴 수 있는 상태를 유지한다.

---

### ADR-0010 — 원본 입력 파일을 절대 수정하지 않는다

**결정:** 입력은 읽기 전용. 출력은 항상 새 파일. 덮어쓰기는 기본 동작이 아니다.
**근거:** 사용자의 원본 소재는 대체 불가능할 수 있다. 안전한 기본값 원칙.

---

## 2. 제안됨 (Proposed)

**아직 확정이 아닙니다. 리뷰어는 반박해도 됩니다.**
반박할 때는 대안과 근거를 함께 제시합니다.

---

### ADR-0011 — 10개 모듈로 분해한다 *(제안됨)*

`ingest` · `audio` · `asr` · `subtitle` · `restore` · `eval` · `orchestrator` · `storage` · `ui` · `export`

**근거:** 자막 경로와 영상 경로를 독립적으로 개발·평가하려면 경계가 필요하다.
**불확실한 점:** 모듈 수가 과할 수 있다. `ingest`를 `audio`/`restore`에 흡수하는 것도 가능.
실제 구현에서 경계가 성가시면 조정한다.
**검증 방법:** Phase 1에서 자막 경로를 만들 때 경계가 방해가 되는지 관찰.

---

### ADR-0012 — 모델을 어댑터 뒤에 격리한다 *(제안됨)*

`AsrAdapter`, `RestoreAdapter` 인터페이스 뒤에 실제 모델을 둔다.

**근거:** 지금 어떤 모델이 최선인지 모른다 (U-22). 코어가 특정 모델 API에 의존하면
그 선택이 영구 부채가 된다.
**비용:** 추상화 계층이 하나 늘고, 모델 고유 기능을 쓰기 어려워질 수 있다.
**허용 조건:** 어댑터가 실제 교체를 방해하면 재검토.

---

### ADR-0013 — 단계별 중간 산출물을 디스크에 보존한다 *(제안됨)*

**근거:** 재실행·디버깅·평가·재개(resume)의 전제. 긴 작업에서 앞단계를 다시 돌리는 것은 큰 낭비.
**비용:** 디스크 사용량. 보관 정책이 필요하다 (U-16).

---

### ADR-0014 — 프로젝트 디렉터리 배치 *(제안됨)*

[`ARCHITECTURE.md`](ARCHITECTURE.md) §3.8의 구조 (`inputs/`, `jobs/`, `outputs/`, `evals/`).

**근거:** 파일 정리는 제품 요구사항이다. 사용자가 결과를 찾을 수 있어야 한다.
**불확실한 점:** 프로젝트 단위가 적절한 입도인지 미검증.

---

### ADR-0015 — 단일 종합 점수를 만들지 않는다 *(제안됨)*

**결정:** 지표를 가중 평균으로 뭉치지 않고 scorecard로 나란히 본다.
**근거:** 가중치 자체가 근거 없는 결정이 된다. 어느 축이 무너졌는지 안 보인다.
**비용:** "좋아졌나?"에 한 줄로 답하기 어렵다. 판단에 사람이 개입해야 한다.
**반대 의견 가능:** 실무에서 단일 지표가 있어야 자동 비교가 편하다는 반론이 가능하다.

---

### ADR-0016 — `is_estimate`는 상수 true다 *(제안됨)*

**결정:** `ReconstructionResult.is_estimate`가 false가 되는 경로를 만들지 않는다.
**근거:** ADR-0002의 기계적 강제. 규칙을 문서에만 두면 지켜지지 않는다.
**대안:** 필드를 아예 없애고 타입 이름으로 표현 (`EstimatedReconstruction`).
구현 시 재검토 가능하나, **의미는 바뀌지 않는다.**

---

### ADR-0017 — UI는 `orchestrator` 위의 껍데기다 *(제안됨)*

**결정:** 모든 기능은 UI 없이 실행 가능해야 한다. UI 전용 기능은 존재할 수 없다.
**근거:** 평가 자동화와 재현성이 UI에 의존하면 안 된다. UI 프레임워크 교체도 쉬워진다.

---

### ADR-0018 — manifest로 재현성을 보장한다 *(제안됨)*

모든 작업이 `input_hash`, `config_hash`, `pipeline_version`, adapter 버전, `seed`를 기록한다.

**근거:** 평가 비교의 전제. 어떤 설정으로 만든 결과인지 모르면 비교가 무의미하다.
**한계:** GPU 커널 비결정성 등은 manifest로 제거되지 않는다. **그 경우 비결정성을 명시**한다.

## 3. 보류됨 (Deferred) — 의도적으로 지금 정하지 않음

| ID | 항목 | 언제 정하는가 | 지금 정하면 안 되는 이유 |
|---|---|---|---|
| U-01 | 구현 언어 / 런타임 | Phase 1 착수 시 | 후보 모델 생태계에 따라 달라짐 |
| U-02 | UI 프레임워크 | Phase 3 | Phase 1–2의 실제 자원 사용량을 봐야 함 |

## 5. 기각된 것 (Rejected)

| 항목 | 왜 기각했는가 |
|---|---|
| 채점 피드백으로 파인튜닝 | 채점 결과를 볼 수 없다. 학습 신호가 존재하지 않는다 |
| 자막·영상을 하나의 파이프라인으로 통합 | 한쪽 실패가 다른 쪽을 막는다. 독립 평가가 불가능해진다 |
| Phase 0에서 프레임워크·모델 확정 | 근거가 없다. 되돌리기 비용만 만든다 |
| 단일 종합 품질 점수를 채점 예측으로 사용 | 채점 방식을 모른다. 예측이라 부를 수 없다 |
| "모자이크 완전 제거" 목표 | 원리적으로 불가능. ADR-0002 위반 |

## 6. 결정을 추가하는 방법

1. 새 ADR 번호 부여 (재사용 금지)
2. **맥락 → 결정 → 근거 → 결과 → 되돌리기** 순으로 기록
3. 상태 라벨을 **반드시** 붙인다 (승인됨 / 제안됨 / 미해결 / 보류됨)
4. 관련 문서에 반영하고 상호 링크
5. 상태가 바뀌면 **이전 내용을 지우지 말고** 변경 사실을 덧붙인다

**기각된 안도 기록합니다.** 왜 안 했는지 남기지 않으면 같은 논의를 반복하게 됩니다.

## 1. 승인됨 (Accepted)

### ADR-0001 — Phase 0에서는 코드를 쓰지 않는다 (문서 우선)

**맥락:** 요구사항이 불확실하고, 서로 대화를 볼 수 없는 여러 에이전트가 병렬 작업해야 함.
**결정:** Phase 0의 산출물은 문서뿐. 기능 코드·의존성·모델·CI·비밀정보를 추가하지 않는다.
**근거:** 공유 전제 없이 시작한 코드는 나중에 전부 버려야 함. 문서는 코드보다 고치기 싸다.
**되돌리기:** Phase 1 진입 시 자연스럽게 해제.

---

### ADR-0002 — "복원"이 아니라 "재구성/추정"으로 기술한다

**맥락:** mosaic·blur는 정보를 실제로 삭제한다. 원본은 알 수 없다.
**결정:** 모든 시각 개선 결과를 재구성(reconstruction) 또는 추정(estimation)으로 기술한다.
**결과:** `is_estimate`는 상수 true (ADR-0016). 모듈·어댑터 이름도 `reconstruct` 계열 (ADR-0026).
**되돌리기:** 없음.

### ADR-0003 — Local-first를 기본값으로 한다

**결정:** 네트워크 없이 동작하는 것이 기본. 클라우드 전송은 사용자가 켜는 선택 기능.
**결과:** `export`가 선택적 주변부가 된다 (Phase 4). 처리 성능은 사용자 PC에 달린다.

### ADR-0005 — 합성 열화를 **주된** 평가 신호로 쓴다 *(범위 정정됨)*

**맥락:** 채점 원본이 비공개라 실제 정답과 비교할 수 없다.
**결정:** 정답을 아는 데이터에 열화를 가해 dev 평가 세트를 만든다.
**정정 (REVIEW-001):** 이전 판은 이를 **"유일하게 신뢰 가능한 신호"** 라고 기술했다. 그것은 과한 주장이다.
합성 열화는 **주된 신호(primary dev signal)** 이며, 자연 실데이터·무참조 지표·사람 blind 검토·
교차 일치도·형식 검사와 **함께** 사용한다 ([`EVALS.md`](EVALS.md) §1.1).
**결과:** 개선 주장은 합성 신호 + 최소 하나의 다른 신호가 같은 방향일 때만 한다.

### ADR-0027 — 운영 구조를 네 역할로 전환한다 *(신규 — 오너 지시)*

**맥락:** 이전 운영은 Claude와 Codex 두 에이전트를 대칭적으로 두고, 독립 리뷰를
Codex(및 Codex Cloud / GitHub `@codex review`)가 맡는 것을 전제했다.
사람 제품 오너가 운영 구조를 바꾸기로 결정했다.

**결정 — 향후 운영은 다음 네 역할로 한다**

| # | 역할 | 책임 | 저장소 커밋 |
|---|---|---|---|
| 1 | **GPT Work** | 전체 오케스트레이션, 요구사항·우선순위 결정 지원, 작업 분해, Claude에 전달할 정확한 프롬프트 작성, 결과 비교와 오너의 최종 판단 지원 | 하지 않음 |
| 2 | **Claude Code Cloud 주 세션** | Lead Developer. 핵심 설계·구현, 복잡한 디버깅, 성능 최적화. TASK Owner | 함 |
| 3 | **독립 Claude Code 리뷰 세션** | Independent Reviewer. 작성자와 **다른 새 세션**, 작성자 대화 맥락 없음. 저장소·TASK·PR diff만 보고 검토. TASK Reviewer | 리뷰 문서만 |
| 4 | **Claude 일반 대화** | 아키텍처 자문, 기술 선택 비교, 막힌 문제의 두 번째 의견 | 하지 않음 |

**함께 결정한 제약**

1. **Codex / Codex Cloud / GitHub `@codex review`는 향후 역할·배정·절차에서 제거한다.**
2. **작성자와 리뷰어는 반드시 서로 다른 Claude Code 세션이다.** 주 세션은 자기 변경을
   스스로 최종 승인하지 않는다 (`AGENTS.md` R8 / §3.1).
3. **Claude 사용량이 제한적이므로** 주 세션은 고난도 구현에 집중하고,
   독립 리뷰는 **중요한 PR과 핵심 알고리즘 변경에만** 사용한다 (`AGENTS.md` §3.2).
4. **두 세션이 같은 파일을 동시에 수정하지 않는다** (`AGENTS.md` R9 / §3.4).
5. **완료 보고만 신뢰하지 않고**, 가능한 경우 GitHub 상태와 diff로 확인한다
   (`AGENTS.md` R10 / §3.5).
6. **AI는 병합하지 않는다.** 병합 결정은 사람 제품 오너만 한다 (ADR-0009 유지).
7. 리뷰어는 **리뷰 대상 브랜치의 파일을 직접 수정하지 않는다** (`AGENTS.md` §3.3).

**역사 기록의 취급**

- 과거에 실제로 수행된 기록 — REVIEW-001이 **Codex/GPT Work를 통해 전달**된 사실,
  TASK-000·TASK-001의 당시 Owner/Reviewer, 기존 커밋의 작성·검토 이력 — 은
  **사실이므로 삭제하거나 다른 주체가 한 것처럼 바꾸지 않는다.**
- 대신 **"완료된 역사 기록"임을 명시**하고, 미래 규칙과 구분한다.
- 과거 TASK 문서 안에 **미래 표준 절차로 남아 있던** Codex 지시·예시 브랜치·다음 리뷰
  지시는 제거하거나 현재 운영 구조로 교체한다.

**왜 "승인됨"인가:** 이 결정은 에이전트가 만든 전략이 아니라 **사람 제품 오너의 지시**다
(상태 표기 규칙 §상태 표기 참조). 근거는 오너 지시이며, 바꾸려면 오너 승인 + PR이 필요하다.

**기록:** [`tasks/TASK-007.md`](tasks/TASK-007.md)

### ADR-0029 — 공식 LID 정확도 채점을 **미지원**으로 두고, 격자 경계만 먼저 고정한다

- **상태:** 승인됨 (2026-08-31, 사람 제품 오너 — TASK-029 D-04 option 3)
- **범위:** [`EVALS.md`](EVALS.md) §4.5 · [`ARCHITECTURE.md`](ARCHITECTURE.md) §3.0.2 ·
  [`tasks/TASK-029.md`](tasks/TASK-029.md) §19

**맥락:** 격자 기반 LID 정확도는 격자 하나에 정답 언어가 **하나**라고 전제한다. 그런데 이
계약은 서로 다른 `stream_id`가 같은 시각을 동시에 덮는 것을 정상으로 허용한다(동시 발화,
EVALS §4.6). 그 시각에 두 stream의 언어가 다르면 정답 label이 하나가 아니고, 하나로 접는
규칙 — 우세 stream, 첫 stream, 하나라도 일치, 그 격자를 분모에서 제외 — 이 저장소 어디에도
없다. 넷 중 무엇을 고르든 **새 채점 규칙을 정하는 일**이며 결과 수치가 달라진다.

**결정:**

1. §4.5 (a)·(b)·(c)의 공식 LID 지표는 `status: "unsupported"`,
   `reason: "simultaneous_multilingual_speech_semantics_undefined"`로 고정한다. `value`는 없다.
   **0점도 100점도 아니다.**
2. 이 미지원은 **데이터에 의존하지 않는다.** "동시 발화가 없는 실행에서만 채점한다"도 규칙을
   고르는 일이므로 하지 않는다.
3. 동시 다국어 발화의 채점 의미는 **후속 화자/정렬 평가 TASK**가 정한다. 그 전에는 지원으로
   바꾸지 않는다.
4. 미지원이어도 **경계는 지금 고정한다** — timeline origin(정준 timebase 0.0초)과 반개구간
   100ms interval, 꼬리 프레임의 중점 규칙, 맞닿은 동일 언어 span의 정규형, 동시 다른 언어
   stream을 집합으로 두고 접지 않는 표현, 분모 0의 명시적 표현(`insufficient_n`, 값 없음).
   기계 정본은 `src/media_clarity/subtitle_contracts.py`이고 fixture는 K-170·K-171이다.
5. 정규형 위반(맞닿은 동일 언어 span)은 TASK-029 validator가 `E_OFFSET_ORDER`로 거부한다.

**근거:** 없는 규칙을 지어내면 그 수치는 근거 없는 숫자가 된다. 반대로 경계까지 열어 두면
후속 구현 둘이 서로 다른 격자로 "같은 지표"를 계산하게 된다. 결정할 수 없는 것(채점 의미)과
지금 결정할 수 있는 것(정규화·경계)을 나눈다.

**결과:** LID 정확도 수치는 당분간 리포트에 숫자로 나오지 않는다. 어려운 구간을 `und`·gap·
복수 언어로 내보내 점수를 올리는 회피 경로도 함께 닫힌다 — 점수 자체가 없기 때문이다.

**되돌리기:** 후속 TASK가 동시 다국어 격자의 채점 의미를 정의하면 새 ADR로 대체 관계를
기록하고 §4.5(a)를 지원으로 바꾼다. 이 ADR이 고정한 다섯 경계를 바꾸려면
`LID_GRID_PROFILE` 이름을 올린다.

### ADR-0004 — 자막을 먼저 착수한다 *(제안됨 — 이전 판의 "승인됨"에서 정정)*

**정정 (REVIEW-001):** 이전 판은 이 결정을 **승인됨**으로 표시하고,
근거로 "과제 채점 대상도 자막이 중심이다"라고 적었다.
**그 근거는 검증되지 않았다.** 배점 비중은 U-24로 미해결이다.

**결정 (범위를 좁혀 다시 진술)**

- 자막을 **먼저 착수**한다. 이것은 **순서 제안**이다.
- 근거는 "자막이 더 중요해서"가 아니라 **"평가 기반을 먼저 세우기 위해서"** 다.
  자막 단계에서 만드는 평가 하네스·`ReferenceBundle`·시간축 계약을 시각 도메인이 재사용한다.
- **범위 축소가 아니다.** 과제는 자막과 시각 재구성을 모두 요구한다
  ([`PRODUCT_SPEC.md`](PRODUCT_SPEC.md) §2, AS-1).

**금지되는 추론:** "Phase 2니까 급하면 버려도 된다."
일정 부족 시의 범위 조정은 **사람 오너의 결정**이다 (AS-4).

**반박 가능 지점:** 시각 재구성을 먼저 하거나 완전 병렬로 진행하는 것도 가능하다.
특히 U-24가 시각 비중이 크다고 밝혀지면 이 순서는 재검토되어야 한다.

### ADR-0012 — 모델을 어댑터 뒤에 격리한다 *(제안됨)*

`AsrAdapter`, `ReconstructionAdapter` 뒤에 실제 모델을 둔다.
어댑터는 `capabilities()`로 **능력을 보고**하고, 코어는 없는 능력을 기본값으로 채우지 않는다
([`ARCHITECTURE.md`](ARCHITECTURE.md) §7.3.1).

### ADR-0018 — 재현성을 **세 등급으로 구분**한다 *(제안됨 — 이전 판 정정)*

### ADR-0021 — 공통 계약과 정준 시간축을 둔다 *(제안됨)*

### ADR-0022 — 재구성 안전 게이트를 둔다 *(제안됨 — 이전 판의 "정책 승인됨"에서 정정)*

**세부 (제안됨, 동일 상태):** `region_class` 목록, 분류 방법, 임계값

#### 4.1.1 U-08 답변 — **번역 자막** (2026-08-09, 사람 제품 오너)

**질문 원문(보존):** "정답 자막은 **원어**인가 **번역**인가?"

**답변:** **채점 정답은 번역 자막입니다.**

| 결과 | 내용 |
|---|---|

2026-08-22 사람 제품 오너가 **한국어(`ko`)** 로 답해 해소했습니다. §4.1.3 참조.

**ADR로 변환하지 않았습니다.** 이것은 사람 오너가 확인해 준 **과제의 사실**이지,
에이전트가 만든 아키텍처 결정이 아닙니다.

### ADR-0028 — Lean Root / Claude Code 분업과 승인 후 통합

- **상태:** 승인됨 (2026-08-24, 사람 제품 오너)
- **대체 관계:** ADR-0027의 미래 역할·리뷰·통합 규칙을 대체한다. 과거 수행 기록은 변경하지 않는다.

**맥락:** 제품 오너는 모바일 환경에서 코드를 직접 작성하지 않는다. Claude Code는 코드 구현에
집중시키고, Lean Root는 저장소 상태·요구사항·비코드 작업·검증·리뷰·통합을 책임지는 편이
세션 비용과 오류 누적을 줄인다. 기존 규칙은 GPT Work의 저장소 변경과 리뷰·병합을 전면 금지해
현재 운영과 충돌했다.

**결정:**

1. 소스·테스트·fixture generator·검증 스크립트·빌드·CI·의존성 등 모든 코드 변경은
   Claude Code가 작성한다. Lean Root는 직접 코드를 쓰지 않고 완결된 구현/수정 프롬프트를 제공한다.
2. Lean Root는 요구사항·작업 분해·비코드 조사와 문서·직접 검증·Claude Code 변경 리뷰·PR 준비를 담당한다.
3. 코드 작성자와 리뷰어를 분리한다. 기본 조합은 Claude Code 작성 / Lean Root 리뷰다.
4. Lean Root는 사람 제품 오너가 특정 PR과 고정 HEAD 병합을 명시적으로 승인한 뒤에만
   `expected_head_sha`를 고정해 일반 merge할 수 있다. 승인 뒤 HEAD가 바뀌면 재승인이 필요하다.
5. Gate L/M은 불필요한 TASK/REVIEW 문서를 생략할 수 있다. Gate H/S은 고정 HEAD 독립 검증,
   직접 재현, 롤백/복구 증거와 사람 승인을 요구한다.

**근거:** 구현과 검토를 다른 행위자로 분리하면 같은 오해를 공유할 위험이 줄고, 반복 판정은
Lean Root가 테스트·검증 스크립트로 시스템화할 수 있다. 병합에 고정 HEAD 조건을 사용하면 승인 뒤
조용히 추가된 변경을 자동으로 차단한다.

**결과:** 코드 수정 루프는 항상 Claude Code 프롬프트로 돌아가며 Lean Root는 자기 작성 코드를
리뷰하는 상황을 만들지 않는다. 비코드 운영 변경은 Lean Root가 직접 처리할 수 있지만 자기 승인하지 않는다.

**되돌리기:** 운영 주체를 다시 바꿀 때는 ADR-0028을 삭제하지 않고 새 ADR로 대체 관계를 기록한다.
진행 중 코드 PR은 기존 작성자·고정 HEAD·승인 경계를 유지한 채 끝내거나 명시적으로 종료한다.

### ADR-0029 — GPT-primary 실행과 제한적 Claude escalation

- **상태:** 승인됨 (2026-08-31, 사람 제품 오너)
- **대체 관계:** ADR-0028의 미래 역할·리뷰·자원 배정 규칙을 대체한다.
  ADR-0006·0009의 협업·병합 절차는 `AGENTS.md`의 현재 규칙으로 좁힌다. 과거 수행 기록은 바꾸지 않는다.

**맥락:** GPT Work/Codex 사용 여유는 커지고 Claude Pro 사용량은 제한적이다. 모든 코드와 반복 검토를
Claude에 고정하면 가장 희소한 자원이 병목이 된다. 반대로 한 세션이 구현·승인·병합 판단을 모두 맡으면
같은 오해가 검증까지 통과할 수 있다.

**결정:** GPT/Codex를 기본 오케스트레이션·작성·검증 자원으로 사용한다. 리뷰가 필요한 변경은
Author와 fresh Reviewer를 분리하고 누구도 자기 변경에 승인 판정을 내리지 않는다. 제품 오너만 병합을
승인하며, Lean Root는 오너가 지정한 PR·전체 HEAD SHA·reviewed base SHA가 유지될 때만 병합을
기계적으로 실행할 수 있다. Claude는 진행 중 기존 계약, 오너의 명시 요청,

근거 교환 뒤의 기술적 교착 중 하나를 기록한 경우에만 쓴다. 상세 절차의 정본은 `AGENTS.md` §3이다.
